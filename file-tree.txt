# Radiant by Provenance — Supply Chain Traceability Platform

Vite + React 19 single-page app. No TypeScript. All styling is inline JSX (no CSS files). Run `npm run dev` for development, `npm run build` to verify.

## Architecture

### App Shell
- `src/main.jsx` — Entry point, renders App.
- `src/App.jsx` — Root component (~55KB). Owns all top-level state: `sel` (selected node), `view` (graph/map/risk), `booted` (boot sequence), `chainRequest`, `attFilter` (unified filter state), `appMode` ('buyer'|'supplier'), `credits` / `supplierCredits` (buyer: 2400, supplier: 2400), `sdaChainContext` (invitation→SDA flow), `sdaMutations` (SDA state map for idempotent recompute), `approvalStates` (asset approval state machine), `evidenceRequests` (evidence request objects from evaluations), and all supplier-mode state. Renders BootScreen overlay, Header, Sidebar (buyer) or SupplierSidebar (supplier), active view or supplier shell, floating DetailPanel, breadcrumb bar, and Footer.

### Components
- `src/components/Header.jsx` — Top bar with Radiant logo, vertical selector, Requirements / "+ Program" / "+ Invite" / "Register Asset" / "Asset Directory" buttons, credits display, account/role menu.
- `src/components/Footer.jsx` — Status bar: network name, view indicator, connection status.
- `src/components/Sidebar.jsx` — Unified filter panel + tree/list view. Metrics row, traceability bars, search, STATUS/CLAIM TYPE/TIER filters.
- `src/components/NetGraph.jsx` — Main buyer-side SVG network graph with pan/zoom, convergence edges, SDA-typed edge rendering, health overlays, provisional node styling.
- `src/components/SubgraphModal.jsx` — 85% viewport modal showing filtered subgraph with own pan/zoom and DetailPanel.
- `src/components/DetailPanel.jsx` (~45KB) — Floating 360px right-side overlay. **Most complex component.** Supports buyer and supplier contexts via `isSupplier` prop. Contains: header (node name, type, health, compliance), SDA cards, invite button, evaluation status section (buyer), evaluation history (supplier), approval state machine (approve/reject/approved status), evidence request cards (both buyer review and supplier response forms), Claims/Timeline tabs with filters, inputs list. Uses "takeover pattern" for Evidence Block and Invite Panel.
- `src/components/EvaluationModal.jsx` — 5-phase modal: Setup → Processing → Results → Review → Complete. PRNG-seeded results, triage, human review with Confirm/Override→Pass/Override→Fail/Request Evidence, adaptive finalize button.
- `src/components/RiskMatrix.jsx` — Attestation health scatter plot.
- `src/components/WorldMap.jsx` — react-simple-maps geographic visualization.
- `src/components/SupplierNetGraph.jsx` — Three-column supplier graph (Org → Assets → Buyers).
- `src/components/SupplierSidebar.jsx` — Supplier-side navigation.
- `src/components/InvitationModal.jsx` — Centered modal for invitation acceptance with type selection.
- `src/components/AssetRegistrationStandaloneModal.jsx` — Standalone asset registration (header button).
- `src/components/AssetDirectoryModal.jsx` — Platform-wide asset browse with search/sort/detail/preview.
- `src/components/SDACreationModal.jsx` — 4-step SDA wizard supporting invitation-driven entry.

### Data Layer
- `src/data/tokens.js` — Design tokens (TT object with type-specific colors/labels).
- `src/data/verticals.js` — Vertical configuration (labels, nodeTypeLabels, tierHierarchy, terminalTypes, inviteRequirements).
- `src/data/generateDataset.js` + `generateFastCo.js` + `generateGovCo.js` + `generateMicroCo.js` + `generateAutoCo.js` — ~2,500 nodes each (AutoCo is 1-node blank-slate).
- `src/data/dataset.js` — `applyCompat()` normalizes `node.attestations` → `node.rawAttestations`.
- `src/data/platformAssets.js` — 80 per-vertical platform assets for Asset Directory.
- `src/data/generateEvents.js` — Network events for notification system.

## Key State (App.jsx)

| State | Type | Purpose |
|---|---|---|
| `credits` | number | Buyer credits (2400 initial) |
| `supplierCredits` | number | Supplier credits (2400 initial) |
| `appMode` | 'buyer'\|'supplier' | Active role |
| `approvalStates` | {[nodeId]: {status, timestamp, reviewer, notes}} | Asset approval decisions |
| `evidenceRequests` | request[] | Evidence requests from evaluations |
| `data` / `sel` / `view` | dataset/node/string | Core navigation state |
| `sdaMutations` | {[nodeId]: sda[]} | SDA state map (flat array per node) |
| `supplierDetailNode` | node \| null | Selected node in supplier graph |
| `evalModalOpen` / `evalModalNode` | boolean/node | EvaluationModal state |

### Evidence Request Schema
```
{
  id: string,          // 'evreq-{timestamp}-{index}'
  nodeId: string,      // target node
  nodeName: string,
  reqId: string,       // requirement ID from evaluation
  title: string,       // requirement title
  outcome: string,     // original AI outcome
  sdaFieldCategory: string|null,
  checklist: string,   // e.g. 'CMMC Level 2'
  status: 'pending'|'submitted'|'resubmitted'|'accepted'|'rejected',
  requestedAt: string,
  requestedBy: string,
  response?: { fileName, fileType, fileSize, notes, submittedAt, submittedBy },
  previousResponses?: response[],  // on resubmit
  reviewedAt?: string,
  reviewedBy?: string,
  reviewNotes?: string
}
```

### Evidence State Machine
```
pending → submitted → accepted (terminal)
                   → rejected → resubmitted → accepted (terminal)
                                            → rejected (loop)
```

### Approval State Machine
```
PROVISIONAL → APPROVED (requires ≥1 evaluation + Approve button)
PROVISIONAL → REJECTED (always available, no eval needed, node removed from tree)
APPROVED → (no undo — revoke SDA to remove, NOT BUILT YET)
```
~97% of nodes pre-seeded as approved. ~3% remain provisional for demo.

### Key Callbacks (App.jsx)
- `handleEvalComplete(node, summary)` — Stores eval record on node, deducts credits, creates evidence request objects from summary.evidenceRequested[], creates network event.
- `handleSubmitEvidence(requestId, responseData)` — Updates evidence request status to submitted/resubmitted, creates network event.
- `handleReviewEvidence(requestId, decision, reviewNotes)` — Updates to accepted/rejected. If accepted: creates 'evidence_accepted' attestation on node, creates network event.
- `onApproveAsset(nodeId, notes)` — Sets approvalStates[nodeId] to approved, adds 'approved_asset' attestation.
- `onRejectAsset(nodeId, reason)` — Sets rejected, removes node from tree via in-place mutation.

## Evaluation System

### Mock Engine (EvaluationModal.jsx)
- PRNG seeded by `nodeId + checklist.id` → deterministic results per node.
- Outcome distribution: ~43% pass_high, ~21% pass_med, ~14% pass_low, ~14% minor_issue, ~7% major_issue/not_evidenced.
- SDA redaction: selective SDA nodes get NOT_EVIDENCED outcomes for redacted field categories.
- Triage: autoApproved (pass_high), needsReview (pass_med, pass_low, minor_issue), flagged (major_issue, not_evidenced).
- Human review: 4 actions per item — Confirm, Override→Pass, Override→Fail, Request Evidence.
- Approve All: bulk-approves all undecided review items.

### Adaptive Finalize Button
1. Any evidence requested → grey "Request Evidence (N) & Finalize →" (evidence DOMINATES)
2. Failures only → red "Fail & Issue Credential →"
3. All passed → green "Finalize & Issue Credential →"

### Credit Cost
10 credits per requirement. Checklists: AS9100 (47 req = 470), NIST 800-53 (126 = 1260), CMMC L2 (72 = 720), ISO 13485 (38 = 380).

## SDA System

### SDA Schema
```
{ id, type: "full"|"selective"|"derivative", status: "active"|"expired"|"pending",
  discloser, receiver, created, expires,
  disclosedFields?, redactedFields?,      // selective only
  sourceEvalId?, evalResult? }            // derivative only
```

### SDA Field Categories (8)
`shipment_details`, `part_identification` (always disclosed), `material_specs`, `processing_specs`, `test_results`, `certifications` (always disclosed), `pricing`, `supplier_identity`

### Multi-SDA Data Model
- `node.sda` — Primary SDA from generator (backward compat).
- `node.sdas` — Complete array. Built idempotently during customerData useMemo.
- `sdaMutations` — `{ [nodeId]: [...sdaArray] }` (flat array, NOT nested object).
- DetailPanel reads: `node.sdas || (node.sda ? [node.sda] : [])`.

## Conventions / Rules

1. **Detail Panel takeover pattern**: Evidence Block and Invite Panel replace content. Close ✕ returns.
2. **SubgraphModal parity**: Features in DetailPanel must work in SubgraphModal's DetailPanel.
3. **Vertical config is single source**: Read from verticals.js, never hardcode.
4. **Do not modify** Risk Matrix, Supply Map, or data generators unless explicitly told.
5. **State mutations through App.jsx**: Components call callbacks, App.jsx handles mutations.
6. **Node insertion**: In-place tree mutation + `setData(prev => ({...prev}))`. Use `createNode` factory.
7. **Invitation-driven disclosure**: No unsolicited SDAs. Buyer invites → Supplier accepts → SDA.
8. **SDA mutations are idempotent**: Write to sdaMutations, increment supplierDataRev. Never mutate node.sdas directly.
9. **Evidence requests live in App.jsx**: `evidenceRequests` state passed to both buyer and supplier DetailPanels.
10. **Supplier-side evidence block must be gated by `isSupplierAsset`** (not inside `!isSupplier`). Structural bug caught in batch 28-fix.
11. **Approval state reads from `approvalStates` map**, not from node properties.

# HANDOFF.md — Radiant Prototype State (March 2, 2026)

## Current State Summary

Radiant is a fully functional React/SVG prototype for a blockchain-based supply chain traceability platform. Attestation-centric data model where every supply chain fact is a verifiable claim. 5 industry verticals (Aerospace, Healthcare, Government/Satellite, Microelectronics, AutoCo). Both Buyer and Supplier roles functional with distinct UX shells. Buyers: navigate supply chain graphs, evaluate nodes against compliance checklists, manage SDAs, approve/reject assets, request and review evidence. The complete invitation→registration→disclosure→evaluation→evidence→approval cycle is functional end-to-end. Vite + React 19, all inline JSX styling.

## Current Architecture

### Evidence System (new in 28)
- **State**: `evidenceRequests` in App.jsx — array of request objects.
- **5-state machine**: pending → submitted → accepted | rejected → resubmitted → accepted | rejected (loop).
- **Two handlers**: `handleSubmitEvidence` (supplier action), `handleReviewEvidence` (buyer action).
- **Network events**: Created on submit, accept, and reject.
- **Attestation**: On acceptance, 'evidence_accepted' attestation added to node.rawAttestations.
- **Mock upload**: Click-to-select generates deterministic filename from requirement title.

### DetailPanel Dual-Rendering
Evidence requests render in two places with different UIs:
1. **Supplier asset view** (`isSupplierAsset` block ~line 419): Shows evidence request cards with Respond/Resubmit buttons, file upload form, status display.
2. **Buyer view** (`!isSupplier` block ~line 623): Shows evidence request cards inside EVALUATION STATUS section with Accept/Reject buttons, submitted file preview, rejection notes form.

### Evaluation Flow (complete chain)
1. Buyer clicks "Run Evaluation" on asset node → EvaluationModal opens
2. Select checklist + evaluator → Run → PRNG generates results → Triage
3. Human reviews flagged items: Confirm / Override→Pass / Override→Fail / Request Evidence
4. Finalize → eval record stored on node.evaluations[], attestation on rawAttestations, evidence request objects created in evidenceRequests state
5. Supplier sees pending evidence requests → submits evidence
6. Buyer accepts or rejects evidence
7. **NOT YET BUILT**: Re-running evaluation reads submitted evidence and boosts scores

## Next: Batch 29 — Detail Panel Tab Restructure + Evidence-Aware Re-Evaluation

### Problem
The DetailPanel is crowded. Evaluation status, approval controls, evidence request cards, invite buttons, and SDA cards all stack above the Claims/Timeline tabs, pushing attestation content below the fold on most screens. Users must scroll past operational machinery to see the actual claims.

### Solution: Tab Restructure
Promote tab bar to just below the header. Four tabs:

1. **Overview** — Approval status/badges, SDA cards, invite button + pending invitations, evidence summary (count badges, not full cards).
2. **Evals** — Evaluation records, "Run Evaluation" button, evidence request cards with full detail (submit/respond/accept/reject).
3. **Claims** — Attestation list with type/status filters (existing claims tab content).
4. **Timeline** — Chronological claim view (existing timeline tab content).

### Solution: Evidence-Aware Re-Evaluation
When buyer clicks "Run Evaluation" on a node that has submitted (or accepted) evidence requests, the EvaluationModal should:
1. Show banner: "1 evidence document attached · compliance_report_Q1.pdf"
2. During result generation, check `evidenceRequests` for matching nodeId + reqId.
3. Requirements whose reqId matches an evidence request with status 'submitted'|'resubmitted'|'accepted' get boosted: outcome becomes `pass_med` (was `not_evidenced`), confidence 0.65+.
4. After finalize, boosted items show PASS · MED instead of NOT EVIDENCED.
5. If all evidence-requested items now pass, the overall evaluation result flips from FAIL to PASS.
6. Evidence requests with accepted status auto-resolve (no duplicate re-request).

### Files Modified

- `EvaluationModal.jsx` — Add evidence-aware scoring path in `generateResults` or `runEval`.
- `App.jsx` — Pass `evidenceRequests` to EvaluationModal (currently not passed).
